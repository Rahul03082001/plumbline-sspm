# Plumbline: Decision Log

Every non-obvious choice in this project, written in plain language.
Each entry says **what** was done, **why**, and **what it costs** (the tradeoff).
If an interviewer asks "why did you do it this way?", the answer is here.

Entries are grouped by area. "Spec" means `Plumbline_Project_Prompt.md`.

---

## A. Language, tooling, dependencies

### A1. Go instead of Python
**What:** The whole service is written in Go (1.27, the current stable release).
**Why:** A scanner spends its life waiting on many API calls at once. Go has
goroutines (very cheap threads), `context` (every call carries a deadline and can
be cancelled), and `errgroup` (run N things in parallel, stop all of them on the
first fatal error) built into the language and standard library. It also compiles
to one static file that runs in a tiny container with no Python runtime to patch.
**Tradeoff:** slower to write while learning; handling loosely-shaped JSON is wordier
than in Python (contained in one helper file, `internal/model/attr.go`).
See spec section 1 for the full interview answer.

### A2. Very few dependencies
**What:** Only 5 direct third-party modules: SQLite driver, YAML parser, Prometheus
client, `x/time/rate`, `x/sync/errgroup`. UUIDs are generated by a 10-line helper
(`model.NewID`) instead of importing a UUID library.
**Why:** Every dependency is code you didn't write but still ship. A security tool
should have a small attack surface. The Go standard library already covers HTTP,
JSON, HTML templates, crypto, embedding files and testing.
**Tradeoff:** a little more code of our own.

### A3. Pure-Go SQLite (`modernc.org/sqlite`)
**What:** The SQLite driver is a pure-Go translation, not the usual C library.
**Why:** With `CGO_ENABLED=0` the binary needs no C compiler and no system
libraries, so it runs in the smallest "distroless/static" image.
**Tradeoff:** a bit slower than the C version; irrelevant at this scale.

## B. Database

### B1. One database connection (`SetMaxOpenConns(1)`)
**What:** The app opens exactly one connection to SQLite.
**Why:** SQLite allows only one writer at a time. With one connection, our own
goroutines simply queue up instead of failing with "database is locked".
WAL mode is still on so the file is crash-safe and fast.
**Tradeoff:** reads wait behind a write. Publishing a scan takes milliseconds, so
nobody notices. A real multi-instance product would use Postgres (see README "Next steps").

### B2. "One active scan per connection" is enforced by the database
**What:** A *partial unique index*: `UNIQUE(connection_id) WHERE status IN ('queued','running')`.
**Why:** If two people click "Run scan" at the same moment, two HTTP requests race.
Checking "is a scan running?" in Go and then inserting leaves a gap where both
pass the check. The index makes the database itself refuse the second insert, so
the race is impossible. We catch that specific error and return 409 with the ID
of the scan that is already running.
**Tradeoff:** none really; it's one line of SQL.

### B3. Timestamps stored as fixed-width UTC text
**What:** Times are written as `2026-11-15T15:42:07.123456789Z`, always UTC, always
9 decimal digits.
**Why:** We sort scans by `created_at` to find "the previous scan". SQLite has no
real date type; it compares text. Fixed width + UTC means text order = time order.
(The driver's default format includes time zone names, which do not sort correctly.)
**Tradeoff:** we format/parse times ourselves in `store.go` (a few lines).

### B4. Added a `retry_after` column to `scans`
**What:** The spec's schema has no place to store "rate limited, try again after X",
but section 7.4 requires showing it. One nullable column was added.
**Why:** Storing it in its own column keeps `error` exactly `"rate_limited"` (easy to
filter and test) instead of packing a timestamp inside an error string.
**Tradeoff:** one small deviation from the written schema.

### B5. Why an attribute is unknown is stored next to the attributes
**What:** `assets.attributes` holds the known values, plus a reserved key `_unknown`
with the reason for each missing one, e.g.
`{"is_admin": true, "_unknown": {"mfa_enabled": {"reason": "permission_denied", "endpoint": "GET /orgs/{org}/members?filter=2fa_disabled"}}}`.
**Why:** The spec says "absent key = unknown", and also that unknown results must
explain *why*. The reason has to be stored somewhere; putting it in the same JSON
keeps the schema unchanged. Rule fields can never start with `_`, so it can't clash.
**Tradeoff:** the typed getters must ignore that one key (they do: rules never ask for it).

### B6. Migrations are plain `.sql` files embedded in the binary
**What:** `internal/store/migrations/0001_init.sql`, applied in order at startup and
recorded in a `schema_migrations` table.
**Why:** No migration tool to install, nothing to forget at deploy time: the binary
upgrades its own database.

## C. Rules engine

### C0. Inventory completeness is separate from known-check coverage
**What:** A failed or partial asset listing hides the overall score and coverage
percentage. The API still reports assessed/total known checks and a separately
named `known_checks_coverage_pct`. The dashboard explains which listings failed,
and both trend lines break at incomplete scans.
**Why:** On a first scan there are no previous assets to carry forward. Three
passing org checks cannot establish 100% overall coverage if repositories could
not be listed. Inventing a count for unseen assets would be equally misleading.
**Tradeoff:** Scores are withheld even if most known checks were assessed. Existing
scans use their stored collection statuses, so this also corrects historical views.

### C1. Strict three-valued logic (as the spec says)
**What:** If *any* field a rule reads is unknown, the result is `unknown`. Example:
"admin without MFA" on a user who is **not** an admin but whose MFA status is
unknown gives `unknown`, not `pass`.
**Why:** It is the simplest rule to explain and it never over-claims. "We could not
read everything this rule needs" is always true when a field is missing.
**Tradeoff / alternative considered:** *Kleene logic* would say: "is_admin is false,
so the AND can never be true, so it's a pass, even without MFA data". That is
also correct and gives higher coverage (in the simulated v2 scan, 3 user checks
become unknown instead of 20). We stayed with the spec's stricter version.
Switching later is a change to one function (`rules.Evaluate`) and its tests.

### C2. Rules are validated at startup, typos included
**What:** Each rule's fields are checked against the normalized schema
(`model.Fields`), operators against the allowed list, and value types against the
field type. The YAML decoder rejects unknown keys (`fail_whn:` is an error).
**Why:** A rule that names a field that doesn't exist would be `unknown` forever and
quietly lower coverage. Better to refuse to start.

### C3. Typed getters return `(value, known)`
**What:** `model.GetBool(attrs, "mfa_enabled")` returns two values. A missing key,
a JSON `null`, or the wrong type all return `known = false`.
**Why:** In Go, a missing bool reads as `false`. If we used plain values,
"we don't know whether MFA is on" would silently become "MFA is off" (or worse,
"admin is false" → pass). The second return value makes "unknown" impossible to ignore.

### C4. Fingerprint = sha256(connection | rule | kind | external ID)
**Why:** It links "the same check on the same thing" across scans, so we can say
"this finding is new" or "this one is persisting". Including connection and kind
means two tenants, or a user and a repo with the same numeric ID, never collide.
External IDs are GitHub's numeric IDs, which don't change when something is renamed.

## D. Configuration and security of the app itself

### D1. `GITHUB_TOKEN` and `GITHUB_ORG` must be set together
**What:** If exactly one is set, the app refuses to start.
**Why:** That's almost always a deploy mistake (forgot to mount the secret). Failing
loudly is better than quietly running without the live scan.

### D2. htmx 2.0.11 is pinned with an SRI hash checked against two CDNs
**What:** The script tag pins `htmx.org@2.0.11` with
`integrity="sha384-2OatzQy1H+Zd/IIrjr1TcuDGqLXeHhbooAyJY1KdQMKnr4LZ22k31GBLdYKHmVjg"`.
The hash was computed from the file downloaded from jsDelivr and confirmed
identical on unpkg.
**Why:** SRI makes the browser refuse the script if the CDN ever serves different
bytes. Computing the hash ourselves (instead of copying one from a blog) means it
matches the file we actually tested.

### D3. Client IP for rate limiting: count trusted proxies from the right
**What:** `TRUSTED_PROXY_HOPS=0` (local) uses the TCP address. On Cloud Run we set it
to `1`, which takes the **right-most** entry of `X-Forwarded-For`.
**Why:** Anyone can send a fake `X-Forwarded-For: 1.2.3.4` header. Proxies *append*
the real address on the right, so the left side is attacker-controlled and the
right side is not. Taking the left-most value would let a visitor dodge the
5-scans-per-minute limit by inventing a new IP on every request.
**Tradeoff:** if the hop count is wrong, the worst case is that everyone shares one
bucket (stricter limit), never that the limit can be bypassed. Verify after deploy.

### D4. Webhook URLs: only `scheme://host` is stored
**What:** For a webhook pointing at `https://chat.example/hooks/T000/B000?token=abc`,
Plumbline stores the name `https://chat.example` and the attribute `url_scheme = https`.
The path and query are thrown away during normalization.
**Why:** Many webhook URLs *are* secrets (Slack-style URLs carry the token in the
path). A security tool must not copy secrets into its own database, logs, or a public
demo page. A test feeds in a URL with a fake token and checks it never shows up.

### D5. Never follow a pagination link to another host
**What:** If GitHub's `Link: rel="next"` header ever points at a different host,
we stop and mark the listing `partial` (reason `untrusted_next_link`).
**Why:** Following it would send our `Authorization` header (the token) to that host.

### D6. Content Security Policy with no inline anything
**What:** `script-src 'self' https://cdn.jsdelivr.net; style-src 'self'; frame-ancestors 'none'`,
no `unsafe-inline`, no `unsafe-eval`. All JavaScript is in `static/app.js`; templates
never use `style="..."`; htmx runs with `allowEval: false`.
**Why:** If an attacker ever got text into the page (say, a malicious repo name),
the browser still refuses to run it. Defence in depth on top of template escaping.
**Tradeoff:** htmx's own small indicator stylesheet is turned off
(`includeIndicatorStyles: false`); our CSS styles the loading state instead.

### D7. Template escaping, plus a test that forbids `template.HTML`
**What:** All pages use Go's `html/template`, which escapes every value by context.
A test fails if `template.HTML(` appears in the web package, and another test
scans a repo literally named `<script>alert("x")</script>` and checks the page
shows it as text.
**Why:** `template.HTML` switches escaping off. Data from GitHub is attacker-controlled
(anyone can name a repo anything), so it must never be trusted as HTML.

## E. GitHub connector

### E1. The simulated tenant fakes GitHub at the HTTP level
**What:** The "simulated" connector is not separate code that invents assets. It is
a fake `http.RoundTripper` (the piece of Go's HTTP client that actually sends a
request) that answers GitHub URLs with embedded JSON in GitHub's real response
format, plugged into the **same** `github.Connector` the live scan uses. In v2 it
answers the 2FA endpoint with a real-looking `403`.
**Why:** The demo then exercises the real client, the real error classification
(403 → permission denied → unknown), the real 404 "Branch not protected" logic,
and the real normalizer. If the live code breaks, the demo breaks too, so the
demo can't quietly lie.
**Tradeoff:** fixtures must use GitHub's exact JSON shapes (good practice anyway).

### E2. Two endpoints beyond the spec's list
**What:** We also call `GET /orgs/{org}/members` (all members) and
`GET /orgs/{org}/outside_collaborators?filter=2fa_disabled`.
**Why:** `members?role=admin` only lists admins, so without the full list there
are no "users" to check. And outside collaborators need their own 2FA filter,
otherwise their `mfa_enabled` would always be unknown. Both need the same
read-only "Members" permission the token already has: no extra access.

### E3. Outside collaborators are known non-admins
**What:** For outside collaborators `is_admin = false` is set as a *known* value.
**Why:** By definition they aren't organization members, so they can't be org owners.
That's a fact, not a guess, so "unknown" would just waste coverage.

### E4. Partial listings make membership three-valued too
**What:** If the "admins" listing failed halfway, a user found in it is `is_admin = true`,
but a user *not* found in it is `unknown`, not `false`.
**Why:** They might be on the page we couldn't read. Same idea as "missing is not removed".

### E5. A bare 429 is treated as a secondary rate limit
**What:** A `429` with no `retry-after` and no rate-limit headers waits 60s (doubling).
**Why:** The spec only describes 403/429 *with* headers. A 429 always means "slow
down", so treating it like a permission error (no retry, mark unknown) would be wrong.

### E6. Primary rate limit waits until reset **plus one second**
**Why:** `x-ratelimit-reset` is in whole seconds and our clock may be slightly ahead
of GitHub's. GitHub's docs say to retry *after* the reset time. One extra second
guarantees "never earlier than GitHub asked".

### E7. Injectable sleeper and clock
**What:** The client takes a `Sleeper` interface and a `Now` function. Production
uses real timers; tests pass fakes that record "wait 60s" and return instantly.
**Why:** Rate-limit tests check the *exact* wait without actually waiting. The whole
connector test file runs in about a second.

## F. Scanning and publishing

### F1. In-process queue: a buffered Go channel + 2 workers
**What:** `RequestScan` inserts a `queued` row and sends the job into a channel with
room for 16 jobs. Two goroutines take jobs from it. If the channel is full, the scan
fails right away with `queue_full` instead of blocking the HTTP request.
**Why:** Simplest thing that works for one instance. A durable queue (Cloud Tasks,
Pub/Sub) would survive restarts, but needs infrastructure. Listed in "Next steps".

### F2. A panic inside a scan can't kill the worker
**What:** Each scan runs inside a function with `defer recover()`. A panic becomes a
`failed` scan with error `panic`, and the worker moves on to the next job.
**Why:** One bad API response shouldn't silently stop all future scans.

### F3. Shutdown: finish running scans, then cancel
**What:** On SIGTERM the app stops taking scans, gives running ones the remaining
part of an 8-second budget, then cancels them. Queued scans that never started are
marked `interrupted`.
**Why:** Cloud Run gives 10 seconds after SIGTERM. 8s leaves margin to close the DB.

### F4. The publish transaction re-reads "the previous scan" inside itself
**Why:** The previous scan's assets and results (needed for carry-forward and
history) are read in the same transaction that writes the new scan, so they are
guaranteed to be exactly the scan that was current at publish time.

### F5. "Not comparable" for the first scan
**What:** The first scan of a connection is stored as `comparable = 1`.
**Why:** There is nothing before it to compare against, and no delta arrow is ever
shown for it, so a "not comparable" badge would only confuse.

### F6. Unreported kinds count as failed collections
**What:** If a connector forgets to report a collection status for some asset kind,
the publisher treats it as `failed` (reason `not_collected`).
**Why:** The safe default. Assuming "complete" could wrongly mark every previous
asset of that kind as removed.

### F7. The simulated cycle continues after a restart
**What:** At startup the simulated connector starts at position
`(number of succeeded scans) mod 4` in the v1, v2, v2, v1 cycle.
**Why:** Locally the database survives restarts, so the story stays consistent.
On Cloud Run the database resets and the count is 0, so it starts at v1.

### F8. A short delay on simulated scans (2s by default)
**What:** `SIMULATED_SCAN_DELAY` makes each simulated scan take 2 seconds.
**Why:** Without it the demo scan finishes in milliseconds, and visitors never see
"queued → running → done" or the "Scan already running" message. The Playwright
test uses 3s so it can click twice reliably.

### F9. Seed scans for every connection on an empty database
**Why:** Cloud Run starts from an empty database. Scanning the simulated tenant (and
the live org, if configured) at startup means the dashboard is never empty.

## G. Web and UI

### G1. Two endpoint families, one service layer
**What:** `/api/...` returns JSON only. `/ui/...` returns HTML fragments only.
Both call the same `scan.Service` functions. A shared `createScan` helper does
"rate limit → request scan → classify the outcome", and each family only renders it.
**Why:** htmx swaps HTML, and API clients want JSON. Putting the logic in one place
means the 409/429 rules can't drift apart between the two.

### G2. htmx is told to swap 409 and 429
**What:** A `<meta name="htmx-config">` tag lists response-handling rules in order:
2xx/3xx swap, **409 and 429 swap**, other 4xx/5xx don't (and show a toast).
**Why:** By default htmx ignores error responses, so "Scan already running" and
"Slow down" would never appear. A Playwright test proves the browser shows them.

### G3. The status fragment polls itself, then becomes the card
**What:** After "Run scan", the server returns a small element with
`hx-trigger="every 1s"` that asks for its own status again. When the scan is done,
the server answers with the refreshed card plus `HX-Retarget` / `HX-Reswap` headers,
so htmx replaces the whole card and polling stops.
**Why:** No JavaScript to write, and polling ends by itself.

### G4. Card DOM ids replace `:` with `-`
**Why:** Connection ids look like `github:acme-demo`. In a CSS selector `#card-github:acme-demo`
the `:` would be read as a pseudo-class, and htmx targeting would break.

### G5. The JSON API hides the score below 60% coverage too
**What:** `score` is `null` when coverage is insufficient, with `coverage_pct` still present.
**Why:** The rule "a score over too little data is misleading" shouldn't depend on
whether you use the UI or the API.

### G6. Score delta arrows only when comparable
**What:** "▲ 5" / "▼ 20" appears only when both scans show a score and the new one is
comparable. A drop after visibility *returns* (e.g. 48 → 28) is shown, because the
posture we can see really is worse; a rise after visibility *drops* never is.

### G7. Times are rendered in UTC, then localized by JavaScript
**What:** The server writes `<time datetime="...">15:42 UTC</time>`; `app.js` rewrites
it in the visitor's own time zone ("3:42 PM").
**Why:** The server can't know the visitor's time zone; the page is still correct
without JavaScript.

### G8. A GET-only catch-all route
**What:** The "page not found" handler is registered as `GET /`, not `/`.
**Why:** With a catch-all for every method, `DELETE /api/connections` would return
404. Being GET-only lets Go's router answer correctly with **405 Method Not Allowed**.

## H. Deploy and CI

### H1. Base images pinned by digest; Actions pinned by commit SHA
**What:** `golang:1.27.4-alpine@sha256:...`, `distroless/static:nonroot@sha256:...`,
and every GitHub Action as `uses: owner/action@<full SHA> # vX.Y.Z`.
**Why:** Tags can be moved to point at different code; digests and SHAs can't. That
protects the build from a compromised upstream tag (a real supply-chain attack pattern).
**Tradeoff:** updates are manual (or via Dependabot/Renovate later).

### H2. Deploy runs only after CI passes on `main`
**What:** The deploy workflow triggers on `workflow_run` of CI and checks it succeeded,
then deploys that exact commit.
**Why:** Nothing that failed tests can reach production.

### H3. Workload Identity Federation, restricted to this repo's `main`
**What:** GitHub's short-lived OIDC token is exchanged for a Google token. The
provider only accepts tokens where `repository == owner/plumbline-sspm` **and**
`ref == refs/heads/main`.
**Why:** No long-lived JSON key exists that could leak. A fork or another branch
can't deploy.

### H4. Deployer can deploy but can't make things public
**What:** The deployer service account has `run.developer` (deploy revisions), not
`run.admin`. Making the service public is a one-time manual command.
**Why:** Least privilege: a compromised workflow can't change who may call the service.

### H5. Runtime service account reads one secret, nothing else
**Why:** If the app were compromised, the attacker gets a read-only GitHub token for
one org, and nothing in Google Cloud.

### H6. Cross-compiling Dockerfile
**What:** The build stage runs on the build machine's architecture
(`--platform=$BUILDPLATFORM`) and cross-compiles to the target.
**Why:** Building for Cloud Run (`linux/amd64`) on an Apple Silicon Mac stays fast,
because Go cross-compiles natively instead of running in emulation.

## I. Testing

### I1. Failure-handling tests first
**What:** The multi-scan sequences (fail → unknown → unknown → fail, missing from a
partial listing, …) run real scans through a real SQLite database and check drift
and "first seen" at **every** step. Rate limits, 401/403/404/5xx, partial
pagination and GET-only are all tested against a fake GitHub (`httptest`).
**Why:** These are the behaviours that make results trustworthy, and the core of
the interview story. They were also checked by deliberately breaking the code
(e.g. making "unknown" forget history) and confirming the tests fail.

### I2. A test keeps `docs/permissions.md` in sync with the code
**Why:** If the connector starts calling a new endpoint, the test fails until the
documentation says which permission it needs.

### I3. Two Playwright tests for the one thing Go tests can't see
**Why:** Server tests prove the 409/429 responses contain the right HTML. Only a real
browser can prove htmx actually puts them on screen (that is what the
`responseHandling` config is for).
